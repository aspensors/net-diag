# net-diag

[![tests](https://github.com/aspensors/net-diag/actions/workflows/tests.yml/badge.svg)](https://github.com/aspensors/net-diag/actions/workflows/tests.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

`net-diag` — диагностическая утилита Python 3.10+ для наблюдения за проблемами доступа к домену на уровнях DNS, TCP, TLS/SNI и HTTPS. Она не изменяет настройки сети и не пытается обходить ограничения: результат — воспроизводимый отчёт для пользователя, владельца сервиса или сетевого администратора.

## Возможности

```text
домен
  ├─ System DNS (socket.getaddrinfo) ─┐
  ├─ Cloudflare DoH + Google DoH ─────┼─ сравнение IP-адресов
  ├─ TCP connect :443 (опция :80) ───┼─ RTT / reset / timeout / unreachable
  ├─ TLS ClientHello с SNI и без SNI ┼─ транспортное сравнение
  └─ HTTPS HEAD/GET ─────────────────┴─ HTTP-код / Location / Server
                                             ↓
                                          verdict + рекомендации
```

- Изолированное ядро `core/`: только стандартная библиотека и `httpx`, без GUI/Rich.
- CLI с live-этапами, цветными статусами и JSON-экспортом.
- Тёмный CustomTkinter GUI: список доменов, журнал по мере проверки, вердикт, экспорт JSON.
- Таймауты TCP/TLS/HTTP-операций и общий дедлайн на домен, включая зависание системного DNS. При превышении лимита сохраняется явно помеченный неполный отчёт.

## Установка

### Arch Linux: консольный режим

```bash
sudo pacman -Syu --needed python python-pip
git clone https://github.com/aspensors/net-diag.git
cd net-diag
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-cli.txt
python main.py --help
```

Если Git ещё не установлен, добавьте пакет `git` к команде pacman. Для CLI не нужны Tk, CustomTkinter или графическая сессия. Все Python-зависимости устанавливаются в `.venv`.

### Графический режим на Arch

В той же папке с активным виртуальным окружением:

```bash
sudo pacman -Syu --needed tk
python -m pip install -r requirements.txt
python main.py --gui
```

В Arch пакет называется [tk](https://archlinux.org/packages/extra/x86_64/tk/). Для запуска GUI нужен рабочий графический сеанс; на сервере используйте CLI.

### Windows PowerShell

После установки Python 3.10+ откройте PowerShell в папке скачанного проекта:

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe main.py --gui
```

Активация окружения не обязательна: можно запускать его Python напрямую. В других дистрибутивах Linux название пакета Tk зависит от ОС.

## Запуск

```bash
# GUI — режим по умолчанию
python main.py

# один домен
python main.py example.com

# несколько доменов, таймаут операции 10 секунд, общий лимит 30 секунд на домен
python main.py example.com example.org --timeout 10 --deadline 30 --json report.json

# файл, одна запись на строку; строки с # — комментарии
python main.py --file domains.txt --port-80

# принудительный GUI, даже если переданы другие параметры
python main.py --gui
```

Сокращённый вымышленный пример консоли (адреса и тайминги не являются результатом живой проверки):

```text
──────────────── example.com ────────────────
OK      DNS (system): 93.184.216.34 (12 ms)
OK      DNS (DoH): 93.184.216.34 (241 ms)
OK      TCP: Успешных handshake: 1/1. (34 ms)
OK      TLS/SNI: TLS с SNI: 1/1 успешно; контроль без SNI: 1/1. (122 ms)
OK      HTTP: HTTPS HTTP 200. (143 ms)
OK      Verdict: OK: Clean: Есть успешная TLS/SNI-проба или HTTPS-ответ ...
```

GUI содержит поле ввода и кнопки `Загрузить файл` / `Запустить` вверху, потоковый журнал этапов в центре, итоговый вердикт и `Экспорт JSON` снизу. Проверка выполняется в фоновом потоке; UI не блокируется.

## Общий лимит времени

```bash
python main.py example.com --timeout 3 --deadline 5 --json report.json
```

`--timeout` ограничивает отдельные сетевые операции. `--deadline` ограничивает всю диагностику **одного домена**, включая системный DNS, DNS внутри HTTPX, DoH, TCP, TLS и HTTP. Значение по умолчанию — 30 секунд; GUI использует тот же лимит. Для нескольких доменов лимит применяется к каждому последовательно. Параметры CLI не настраивают GUI.

Каждый домен проверяется в отдельном процессе через `spawn`. Родитель получает снимки отчёта по завершении этапов и по истечении дедлайна завершает сетевой процесс. Зависший вызов DNS не остаётся фоновым потоком приложения. Ожидаемая длительность — дедлайн плюс небольшие накладные расходы ОС и до 1,5 секунды ограниченного ожидания очистки процесса/канала; это не гарантия реального времени при остановке или перегрузке ОС.

При превышении лимита JSON получает `"timed_out": true`, вердикт — `Inconclusive`, код завершения CLI — `1`. Данные завершённых этапов сохраняются. Неполученные данные остаются пустыми, а не объявляются сетевой блокировкой. Пробы незавершённого этапа могут не попасть в последний снимок. Обычный отчёт содержит `"timed_out": false`. GUI показывает неполный результат, снова разрешает запуск и позволяет экспортировать JSON.

Для программного использования применяйте `core.runner.DiagnosticRunner(ProbeOptions(...)).check(domain)`. При запуске из собственного скрипта нужен стандартный guard `if __name__ == "__main__":`, как описано в [документации Python о multiprocessing](https://docs.python.org/3/library/multiprocessing.html#the-spawn-and-forkserver-start-methods). `core.checker.NetworkChecker` — низкоуровневый движок для дочернего процесса; сам по себе общий дедлайн он не обеспечивает.

## Матрица вердиктов

| Вердикт | Наблюдаемое условие | Рекомендация |
|---|---|---|
| `OK: Clean` | Есть успешная TLS/SNI-проба или HTTPS-ответ без обнаруженных маркеров страницы-посредника; более специфичных наблюдений нет | Сохранить базовый отчёт; это не подтверждение успешности всех этапов |
| `DNS Poisoning Detected` | Непересекающиеся ответы DNS, фактические неудачные TLS-пробы для **всех** system IP и успешная TLS-проба по DoH | Исследовать расхождение маршрутов; оно само по себе не доказывает подмену |
| `IP Blacklist / TCP Drop` | Есть TCP/443-пробы, все завершились timeout/reset/unreachable, нет успешной TLS/SNI-пробы или HTTPS-ответа | Проверить маршрут, firewall и ACL; причина ещё не установлена |
| `DPI SNI Block` | TCP/443 есть, все TLS с SNI неудачны, хотя бы одна успешная контрольная проба без SNI относится к **тому же IP**; нет успешного HTTPS-ответа | Исключить проблему сервера/TLS; наблюдение не доказывает наличие DPI |
| `HTTP Hijack / Redirect Block` | Редирект/Server содержит маркеры промежуточной страницы | Проверить заголовки, сертификат и сравнить другую сеть |
| `Inconclusive` | Недостаточно успешных проб | Повторить позднее или из другой сети |

Это эвристики, а не доказательство типа оборудования или действий провайдера. Разные ответы DNS сами по себе не считаются подменой: CDN, GeoDNS, split-horizon DNS, captive portal, IPv6-маршрутизация и политика самого сайта могут создавать похожие признаки. TLS-контроль сознательно отключает проверку сертификата **только** для изоляции эффекта SNI; прикладная HTTPS-проба использует стандартную проверку сертификата.

Названия вердиктов сохранены для совместимости с существующим JSON. Слова `Detected`, `Block` и `Clean` в них — исторические метки эвристик, а не доказательство причины или гарантия безопасности. При наличии нескольких наблюдений сначала показывается расхождение DNS/TLS, затем HTTP-маркеры, затем ошибки TCP/SNI. Успешный HTTP-ответ не отменяет отдельное расхождение DNS.

## Пример разбора проблемы

Допустим, браузер не открывает домен. `net-diag` показывает разные адреса system DNS и DoH. Это ещё не вывод о подмене: ответы могут различаться из-за CDN. Если TLS работает только по DoH-адресу, изучите, были ли вообще проверены все системные IP: число кандидатов ограничено. Далее сравните маршруты и повторите проверку из другой сети. Передайте администратору наблюдаемые ошибки, адреса и время проверки, сохранив ограничения вывода.

## Тесты и CI

```bash
python -m pip install -r requirements-cli.txt
python -m unittest discover -s tests -v
```

33 теста проверяют классификацию, неполные пробы, сопоставление IP в SNI-контроле, валидацию таймаутов, JSON-экспорт, коды завершения и вывод русской справки в Windows. Тесты дедлайна запускают настоящие дочерние процессы с намеренно зависшими заглушками DNS и других этапов: проверяют сохранение частичного отчёта, остановку процесса и очистку читающего потока. Отдельно проверяется вызов из фонового потока, как в GUI. Внешняя сеть заменена заглушками, GUI не запускается. GitHub Actions выполняет проверки на Python 3.10–3.14 в Linux и Python 3.12 в Windows. Это проверка логики и запуска CLI; реальные сетевые условия и GUI требуют отдельной ручной проверки. В Windows stdout/stderr настраиваются на UTF-8, включая вывод в файл или канал.

Коды завершения CLI: `0` — отчёты построены для всех доменов без превышения дедлайна, `1` — дедлайн, частичный сбой или ошибка записи JSON, `2` — ошибка аргументов/ввода либо ни одного отчёта. Сетевой отказ внутри построенного отчёта сам по себе не меняет код завершения. JSON сохраняет и полные, и полученные по дедлайну неполные отчёты. Если ошибка вообще не позволила построить отчёт, она остаётся в консоли.

```text

├── core/
│   ├── models.py       # dataclass-модели и перечисления
│   ├── checker.py      # DNS / DoH / TCP / TLS / HTTP пробы

├── requirements-cli.txt # зависимости CLI и ядра
└── requirements.txt    # полный набор с GUI
```

## Ограничения и эксплуатация

Проверяйте только домены и сети, для диагностики которых у вас есть разрешение. DoH-провайдеры должны быть доступны из вашей сети; их недоступность не считается доказательством фильтрации. HTTP-проба намеренно не следует редиректам, чтобы сохранить первичный `Location` для отчёта. JSON включает этапы, ошибки, тайминги и заголовки ответа — перед передачей третьим лицам проверьте его на чувствительные данные.

Проверка использует системный DNS, публичные DoH-сервисы Cloudflare/Google и соединяется с найденными адресами и целевым HTTPS-сайтом. Внешние сервисы получают соответствующие запросы. Прокси-переменные окружения HTTPX игнорируются (`trust_env=False`).
